# 指令调度器：现在怎么做，哪里有错，准备怎么改

这次要做的事只有一个：**在不改变计算结果的前提下，调整指令先后顺序，减少等待。**

下面的“现在”指当前仓库代码；“准备改”还没有实现。原来的实现计划没有修改。

**1. 现在打开 `--schedule`，代码会做什么？**

程序已经生成汇编文字以后，[compiler.py](/home/master/dev/ScratchV/scratchv/compiler.py:462) 才调用调度器。它依次做这几件事：

| 步骤 | 现在做什么 | 对应函数 |
|---|---|---|
| 读汇编 | 把每行拆成指令名和参数，记录它读写哪些寄存器 | `parse_instructions` |
| 记录先后关系 | 例如第二条要用第一条的结果，就记下“第一条必须在第二条前面” | `build_dag` |
| 算优先级 | 试图判断哪条指令后面还有更多计算在等它 | `_compute_priorities` |
| 排顺序 | 从可以安排的指令里挑优先级最高的一条，反复挑到结束 | `schedule` |
| 输出 | 用指令名和参数重新拼成汇编文字 | `compiler.py` 中的字符串拼接 |

其中 `build_dag` 里的“图”没有额外的神秘含义：每条指令是一个点，“A 必须在 B 前面”就是从 A 到 B 的一条连线。

它已经有了排序的基本步骤，也已经处理了一部分寄存器先后关系。但下面这些地方会让它排错，或者无法判断是否变快。

**2. 读完再拼回去，会丢掉原来的汇编内容**

**现在怎么做：**解析时丢掉独立标签等内容；输出时只拼“指令名 + 参数”，不使用已经保存的原始行。

例如输入中有：

```asm
.text
.globl demo
demo:
  lw t0, 0(a0)  # 读取输入
```

当前代码会丢掉 `demo:` 和注释，还会把 `.text`、`.globl` 变成 `text`、`globl`，混进待排序的指令里。这个问题已经实际运行复现。

原因可以直接在 [parse_instructions](/home/master/dev/ScratchV/scratchv/backend/inst_scheduler.py:389) 里看到：它先删掉开头的点，再检查“是否以点开头”。到了检查时，点已经没了。

**准备怎么改：**每一行原文都留着。排序只改变允许移动的那些行的位置，输出时直接取原文。标签和汇编指示行留在原处；行尾注释随指令移动；独立注释和空行第一版直接作为分隔。没有换序时，输出应该和输入逐字相同。

仓库已有 [_asm_parser.py](/home/master/dev/ScratchV/scratchv/backend/_asm_parser.py:30)，能保存原始行、标签和注释，直接复用，不再写一套丢信息的解析器。

**LLVM 参考什么：**[MachineScheduler.cpp 的 `moveInstruction`](/home/master/dev/llvm-project/llvm/lib/CodeGen/MachineScheduler.cpp:1024) 移动的是已有指令对象。我们借鉴“移动原来的指令，保留附带内容”这件事。保存汇编原文的具体代码用 ScratchV 自己已有的解析器；LLVM 这里没有可照搬的汇编文本处理代码。

**3. 现在可能先跳走，再执行本来应该做的事**

**现在怎么做：**把解析出来的指令放在一个列表里排序，没有按标签、分支、调用划分范围，也没有强制跳转留在末尾。

这两条就能复现问题：

```asm
sw  t0, 0(a0)       # 先把 t0 存进内存
beq a1, a2, done    # 再判断是否跳走
```

当前调度器会排成：

```asm
beq a1, a2, done
sw  t0, 0(a0)
```

如果条件成立，存内存这件事就不做了。程序的行为已经改变。

**准备怎么改：**先切成若干小段，再分别排序。指令不能跨标签、调用或跳转移动。分支和返回固定在本段最后；如果末尾是“条件分支 + 无条件跳转”，两条都固定，原顺序不变。

```text
函数标签             保留
几条普通指令         只在这里面排序
调用另一个函数       固定
另外几条普通指令     只在这里面排序
返回                 固定
```

遇到看不懂的指令，也在这里截断。不能因为不知道它会做什么，就允许别的指令跨过去。

**LLVM 参考什么：**[MachineScheduler.cpp 的 `isSchedBoundary` 和 `getSchedRegions`](/home/master/dev/llvm-project/llvm/lib/CodeGen/MachineScheduler.cpp:750)。它们负责找出可以单独排序的范围，本地这版 LLVM 也把调用作为不能跨越的边界。

**4. 现在有些指令的“读什么、写什么”认错了**

寄存器就是 CPU 里存数值的位置，`t0`、`a0` 等是它们的名字。排序之前必须知道每条指令会读哪个位置、覆盖哪个位置。

**现在怎么做：**主要靠“第一个参数通常是写入位置”和几个字符串规则猜测。见 [parse_instructions](/home/master/dev/ScratchV/scratchv/backend/inst_scheduler.py:408)。

有三个具体问题：

| 指令或写法 | 实际含义 | 当前遗漏 |
|---|---|---|
| `lw t0, -4(sp)` | 用 `sp` 算地址，把读到的数放进 `t0` | 识别地址的规则只接受没有负号的偏移，漏掉读取 `sp` |
| `ret` | 跳到 `ra` 保存的返回地址 | 文本没有参数，当前记录成不读取任何寄存器 |
| `t0` 和 `x5` | 同一个寄存器的两个名字 | 按不同字符串处理，漏掉它们之间的先后关系 |

前两项已运行确认。第一项漏掉以后，调度器就可能允许 `sp` 的修改越过这条 load，让它访问另一个地址。

**准备怎么改：**按指令名写清楚读写规则。例如：

| 指令 | 读取 | 写入 |
|---|---|---|
| `add t0, t1, t2` | `t1`、`t2` | `t0` |
| `lw t0, -4(sp)` | `sp` | `t0` |
| `sw t0, 0(a0)` | `t0`、`a0` | 不写寄存器，但写内存 |
| `beq t0, t1, done` | `t0`、`t1` | 不写寄存器，但可能跳走 |
| `ret` | `ra` | 不写寄存器，但会跳走 |

先统一寄存器名字，再比较读写。`zero/x0` 永远是零，不会被真正改写。浮点寄存器的别名也要处理；浮点运算还可能修改异常标志，不能只列出表面上的参数。

共享解析器可以帮忙拆行，但它现有的通用读写判断仍然不够，不能直接当成这张完整的规则表。指令形式不符合已知规则时，就固定在原处。

**LLVM 参考什么：**[ScheduleDAGInstrs.cpp 的 `addPhysRegDeps`](/home/master/dev/llvm-project/llvm/lib/CodeGen/ScheduleDAGInstrs.cpp:303)。LLVM 的操作数已经标明是读还是写，这个函数直接使用这些信息，并处理寄存器的共同物理身份和常量寄存器。我们需要先用自己的规则表补出这些信息，再做同类判断。

**5. 就算认对了读写，当前先后关系也没记全**

**现在怎么做：**[build_dag](/home/master/dev/ScratchV/scratchv/backend/inst_scheduler.py:184) 只记了两类关系：前面写、后面读；前面写、后面又写。

漏掉的是：**前面还要读旧值，后面不能抢先覆盖。**

```asm
add t1, t0, t2    # 用旧 t0 算 t1
mul t0, t3, t4    # 算完以后覆盖 t0
```

假设旧 `t0=10`、`t2=1`、`t3=2`、`t4=3`。原序得到 `t1=11`。当前调度器实际会把乘法提前，结果就变成 `t1=7`。

**准备怎么改：**三种关系都要保留：

- 先写后读：先算出数，才能用它。
- 先读后写：旧数读完，才能覆盖。
- 先写后写：后一次写入必须仍然在后面，否则最后留下的数会变。

代码里给每个寄存器记两笔账：“最近是谁写的”“写完以后有哪些指令读过它”。碰到下一次写入，就要求前面的读取先完成。设计文档里的 RAW、WAR、WAW，分别就是上面这三件事。

**LLVM 参考什么：**[addPhysRegDataDeps](/home/master/dev/llvm-project/llvm/lib/CodeGen/ScheduleDAGInstrs.cpp:247) 处理写后读，[addPhysRegDeps](/home/master/dev/llvm-project/llvm/lib/CodeGen/ScheduleDAGInstrs.cpp:313) 处理另外两种。LLVM 中分别叫 `Data`、`Anti`、`Output`，对应关系相同。

内存还有一个单独的遗漏。当前代码没有记“谁先读写内存”，因此这两条也会被交换：

```asm
sw t0, 0(a0)     # 把新数存进去
lw t1, 0(a0)     # 读出刚存的新数
```

交换后，`t1` 读到的是原来的旧数。

**准备怎么改：**第一版所有读写内存的指令彼此保持原顺序。它们之间仍然可以穿插无关计算，只是不能把这些访存指令互相颠倒。

**LLVM 参考什么：**[ScheduleDAGInstrs.cpp 的 `addChainDependency`](/home/master/dev/llvm-project/llvm/lib/CodeGen/ScheduleDAGInstrs.cpp:560) 会检查两次访存是否可能碰到同一块内存，再决定是否限制顺序。ScratchV 目前没有足够的信息做这种判断，所以第一版全部保序。这是我们做的简化，LLVM 本身没有把所有访存一律锁死。

**6. 现在“先做谁”的分数也算错了**

**现在想做什么：**后面有一长串计算等着某条指令，就优先启动它。这就是文档里说的“关键路径优先”。

例如三条指令依次相互依赖：

```asm
lw  t0, 0(a0)      # 读内存，按 2 拍算
mul t1, t0, t2     # 等 t0，乘法按 3 拍算
add t3, t1, t4     # 等 t1，加法按 1 拍算
```

如果分数表示“从这里开始，到这串计算结束还要多久”，应该从末尾往前算：

```text
add：1
mul：3 + 1 = 4
lw ：2 + 4 = 6
```

当前代码实测给这三条的分数却是 `4、6、1`。

**哪里错了：**[_compute_priorities](/home/master/dev/ScratchV/scratchv/backend/inst_scheduler.py:228) 已经把后面的指令先收集好了，计算时又把列表反转，导致读取后继分数时它还没算好。另外，连线中已经记了前一条的等待时间，公式又把它自身的时间加一次，重复计算。

**准备怎么改：**先算后面的，再算前面的；同一段等待只算一次。上面这个例子的测试直接检查 `6、4、1`，而不是只检查“分数大于零”。遇到分叉就取最长的那条后续计算链。

**LLVM 参考什么：**[ScheduleDAG.cpp 的 `SUnit::ComputeHeight`](/home/master/dev/llvm-project/llvm/lib/CodeGen/ScheduleDAG.cpp:294)。它会先把后继算完，再用“后继的值 + 连线上的等待时间”计算当前值。我们借鉴这个计算顺序和不重复计时的做法；例子中的分数还包含最后一条指令的完成时间，不声称与 LLVM 内部的数值定义完全一样。

**7. 现在的时钟没有模拟出“等待期间可以做别的事”**

**现在怎么做：**只要前面的指令已经排进输出，就认为后面的可以选。选完一条以后，时钟直接加上它的全部延迟。这个时钟又没有用来筛选下一条指令。

例如读内存要两拍，代码就把时钟直接加二。中间本来能做别的计算的那一拍，没有被认真安排。`ready_time` 字段虽然存在，但当前写进去的是选中时的时钟，没有用它判断结果何时可用。

独立的 [estimate_cycles](/home/master/dev/ScratchV/scratchv/backend/inst_scheduler.py:319) 更简单：把所有指令的延迟相加。因此只要指令没增删，不管怎么换顺序，报告数字都一样。

**准备怎么改：**分清两件事：“这条已经开始了”和“这条的结果可以用了”。第一版规定每拍最多开始一条指令；读内存两拍后能用，加法一拍后能用。

```asm
# 原序                    # 改后的一个合法顺序
lw   t0, 0(a0)            lw   t0, 0(a0)
add  t1, t0, t2           addi t3, t3, 1
addi t3, t3, 1            add  t1, t0, t2
ret                       ret
```

| 第几拍 | 原序在做什么 | 换序后在做什么 |
|---|---|---|
| 0 | 开始读内存 | 开始读内存 |
| 1 | 等 `t0` | 计算不需要 `t0` 的 `addi` |
| 2 | `add` | `add` |
| 3 | `addi` | `ret` |
| 4 | `ret` | 已完成 |

这个模型下是 5 拍变 4 拍。若当时没有任何能做的指令，就记录等待；不往汇编里加 `nop`。

除法还要多记一件事：除法单元忙着时，下一条除法得等；不依赖它的普通加法可以继续。为此会分别记录“结果什么时候能用”和“哪个计算单元什么时候空闲”。

换序前后都按同一套规则重新算。只有新顺序更快才使用；一样快或更慢就保留原序。报告列出原序耗时、最终耗时、少等几拍和移动了几条指令，写明是模型估算。

已有 `--cycle-stats` 是另一套五级流水线估算。它和这里的计时含义不完全相同，本次先不重写它，也不把两份报告的数字混着相减。

**LLVM 参考什么：**

- [PostRASchedulerList.cpp 的 `ListScheduleTopDown`](/home/master/dev/llvm-project/llvm/lib/CodeGen/PostRASchedulerList.cpp:544)：把“还要等”的指令与“现在可以执行”的指令分开，检查是否能够执行，再推进时钟。这是本次排序循环最直接的参考。
- [RISCVSchedRocket.td](/home/master/dev/llvm-project/llvm/lib/Target/RISCV/RISCVSchedRocket.td:64)：分别记录结果延迟和计算单元占用时间。借鉴字段怎么分，不照抄 Rocket 的具体数值；例如那里部分除法用 34 拍，本计划的教学模型用 16 拍。

**8. 现在排错了，没有一道检查把它拦下来**

**现在怎么做：**排完直接交给编译器输出。如果剩下的指令都无法选中，[schedule](/home/master/dev/ScratchV/scratchv/backend/inst_scheduler.py:295) 就退出循环，甚至可能只返回已经排好的一部分。

现有测试也偏弱。例如 [test_waw_dependency](/home/master/dev/ScratchV/tests/test_inst_scheduler.py:171) 只检查有两个节点，没有检查两次写入是否建立了先后关系；优先级测试只检查分数大于零。前面那些错误可能不被这些检查发现。

**准备怎么改：**先在临时列表中排序，检查通过再输出。检查这些具体问题：

- 原来的每条指令是否都还在，有没有丢失、重复或改写。
- 有没有越过标签、调用、跳转等边界。
- 每次读取是否仍然读到原来那次写入的值，最后留下的值是否一致。
- 访存的相对顺序有没有改变。
- 新顺序在同一模型里是否真的更快。

发现错误时，按已经讨论的决定：恢复这一段原序，报告哪一段出了什么错；测试使用严格模式，直接失败，不能把部分结果写进输出文件。

测试会用前面的两行反例直接断言顺序，还要把调度前后的汇编分别装配、执行，比较输出。现有 CNN 数值测试有一部分执行的是调度之前的 IR，见 [scratchv_output](/home/master/dev/ScratchV/tests/test_cnn_pipeline.py:105)。它不能证明调度后的汇编正确，需要单独补汇编执行对比。

**LLVM 参考什么：**[MachineScheduler.cpp 的 `VerifyScheduling`](/home/master/dev/llvm-project/llvm/lib/CodeGen/MachineScheduler.cpp:550) 可以在调度前后调用机器指令检查。我们借鉴“排序前后要检查”，不把它说成程序等价证明。恢复原序并警告是本项目已经选定的处理方式，不是照搬 LLVM。

**9. 这些修改会放在哪里？**

| 文件 | 准备改什么 |
|---|---|
| `inst_scheduler.py` | 按范围分段、补齐先后关系、修正优先级、按结果就绪时间排序；完整汇编输出复用原文 |
| 新建 `schedule_semantics.py` | 集中写清楚每种指令读写什么、有没有访存或跳转、哪些形式暂时不能移动 |
| 新建 `schedule_model.py` | 记录指令等待时间和计算单元占用；按给定顺序计算耗时 |
| 新建 `schedule_verify.py` | 检查有没有漏指令、错误覆盖、跨范围移动等问题 |
| `compiler.py`、`main.py` | 在现有 `--schedule` 位置接入，传回报告和警告，增加严格检查选项 |
| 调度测试和 benchmark | 检查具体顺序、具体周期、实际执行结果；性能用例使用合法的寄存器和指令 |

当前默认寄存器分配器已经输出汇编文字，见 [compiler.py](/home/master/dev/ScratchV/scratchv/compiler.py:407)。这次继续在这里之后处理，默认分配器不用改。

LLVM 处理的是尚未打印成汇编的机器指令对象，所以它能直接取得很多我们需要补出来的信息。**参考 LLVM 的依赖规则、分段方法和排队计时方法，不等于要把 ScratchV 改成 LLVM 的整套结构。**

review 里还有一个说法需要纠正：普通 `MachineScheduler` 并不是只在寄存器分配之后运行；[本地源码](/home/master/dev/llvm-project/llvm/lib/CodeGen/MachineScheduler.cpp:376) 明确写着它在分配之前，另有后期调度入口。因此这次主要参考 `PostRASchedulerList` 的排序过程，而不是根据 review 的名字对应关系决定实现位置。
